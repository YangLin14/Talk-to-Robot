The policy-evaluation script `scripts/eval_policy_fetchpush.py` loads the saved checkpoint (`models/sac_her_FetchPush-v4_seed0_best.zip`), resets the environment with a configurable seed, and optionally overrides the env's randomly-sampled goal by writing the supplied vector to `env.unwrapped.goal` and patching the first observation's `desired_goal` field. Per-episode records (`success`, `final_distance`, `steps`, `achieved_goal`, `desired_goal`) are printed and can be written to JSON for downstream analysis. The script's two modes correspond to ablation row A (controller-only sanity, env-sampled goals) and rows D/F (injected goals from a grounder).

The regex baseline lives in `baselines/regex_grounder.py` and exposes a single `ground(instruction, tier, context=None)` entry point. The return shape -- `{instruction, tier, goal, grounder, success, failure_mode, raw_match, notes}` -- is the shared schema the Gemini grounder mirrors, so the W3 eval harness stays grounder-agnostic. T0 uses a numeric-coordinate regex (with or without parens, 2D or 3D), T1 keyword-matches against the shared region table, and T2 parses `<n> <unit> <direction>` phrases, converts centimeters to meters, and applies the offset to a cube position supplied via `context`. T3 and T4 deliberately return `success=False` with `failure_mode="unsupported_tier"` so the eval harness records them as a fair-baseline limit (proposal §8, condition F) rather than as parse errors that would bias the comparison against regex.

The LLM grounder lives in `grounding/` and exposes the same `ground(instruction, tier, context=None, prompt_variant=...)` entry point. `client.py` wraps the official `google-genai` SDK and reads `GEMINI_API_KEY` from a gitignored `.env` at the project root via `python-dotenv`. `prompts.py` provides three builders -- zero-shot, few-shot (three exemplars consistent with `workspace.py`), and chain-of-thought -- all sharing the same workspace description so the model sees exactly the coordinate frame the regex grounder and instruction-library ground truth use. `parser.py` extracts the goal from the model's text response, tolerating raw JSON, fenced JSON, and JSON embedded in trailing prose; missing z components default to the table height. `classifier.py` labels failures as `refusal | parse_error | hallucination | out_of_workspace`, leaving ground-truth-aware classification (region misidentification, etc.) for the eval harness. The whole stack was smoke-tested against the live Gemini 2.5 Flash API across all five tiers with the three prompt variants; LLM and regex outputs agreed exactly on the four T1 corner cases and on the T2 right/forward offset cases.

## Coordinate-frame decisions (now locked in `workspace.py`)
The team had four open coordinate-frame questions blocking the instruction library. We locked them and exposed them as a single source of truth in `workspace.py`; both grounders and the upcoming eval harness import from there. The four decisions:

1. **Goal dimensionality** -- 3D `[x, y, z]`. The proposal text uses 2D for human readability but FetchPush-v4's `desired_goal` is shape `(3,)`. Grounders that emit only `(x, y)` get `z = TABLE_Z` filled in automatically.
2. **Workspace bounds** -- `x ∈ [1.19, 1.49]`, `y ∈ [0.60, 0.90]`. These mirror FetchPush-v4's default goal-sampling region (gripper-init xy `(1.34, 0.75)` ± `target_range=0.15`), so T1 region targets land inside the trained policy's competence zone.
3. **Axis convention** -- robot frame: `+x` forward (away from the robot base), `+y` to the robot's left, `+z` up. "Right" maps to `-y`. Mental model: an observer standing behind the robot looking at the table.
4. **Region semantics** -- top-down view from behind the robot: "upper" / "top" / "far edge" = `+x = x_max`; "lower" / "bottom" / "near edge" = `-x = x_min`; "left" = `+y`; "right" = `-y`. So "upper-left corner" = `(x_max, y_max)`, "lower-right corner" = `(x_min, y_min)`. This convention is also written into the LLM prompt verbatim so Gemini doesn't have to infer it.

Decisions 2 and 4 produced corrections to the original regex grounder: the workspace was off by ±4 cm on x and ±5 cm on y, and the region table had "upper-left" mapped to `(x_min, y_max)` rather than the corrected `(x_max, y_max)`. Both have been fixed.
